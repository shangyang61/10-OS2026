## 二 关键设计：把真实阶数记在块首

交接文档指出：SLUB 大对象保存的是请求页数，
`free_pages(base, n)` 只拿到 n，而 Buddy 可能给了更大的块。
若释放时只按 n 归还，会丢页或误拆别人的块。

本实现的处理：

```c
alloc_pages(3)        // need = ceil(log2(3)) = 2，返回 4 页块
base->property = 2;   // 在块首记录真实阶数
free_pages(base, 3)   // 从块首读回 2，完整归还 4 页
```

释放时另外校验 `2^order >= n > 2^(order-1)`，确保调用者的请求
和块的阶一致；不一致直接断言失败，而不是悄悄接受。

这条设计让现有 `slub.c` 无需改动即可在 Buddy 下正确工作：
大对象保存的请求页数重新算出的阶，与分配时记录的阶一致。

## 三 两套页管理器分开测试的原因

`member2_page_check` 和 `slub_check` 里有 Best-Fit 专属假设：

- `alloc_pages(全部空闲页)` 必须一次成功；
- 同一长度选低地址块，且返回精确物理地址；
- 释放 n 页即归还 n 页。

Buddy 下空闲区由多种阶的块组成，第一条可能合法失败；第二条不适用；
第三条由块首记录的阶决定。因此：

- `PMM=best_fit`（默认）：保持原路径，原始 `make grade` 仍为 20/20。
- `PMM=buddy`：不运行 `member2_page_check`，改跑成员三的 Buddy 测试。
- `slub_check` 在 Buddy 下改用逐页耗尽构造 OOM，其余断言不变。

## 五 本轮修复的问题

1. **`nr_free` 重复计数**：合并时按合并后的阶累加，伙伴页被计两次；
   改为按传入块自身的阶先加一次。
2. **超大长度死循环**：`buddy_order_of` 在 n 超过最大块时，
   `pow2_or_zero` 返回 0 导致 `0 < n` 恒真；改为在 `NR_ORDERS` 饱和。
3. **测试自身的错误假设**：最初假设 2048 B 对象一页可放两个，
   实际页头占用后只能放一个；改为不硬编码页头大小，只验证
   "存在同页共享且页数增长小于对象数"。
4. **Best-Fit 专属 OOM 写法**：`alloc_pages(全部空闲页)` 在 Buddy 下
   合法失败，改为逐页持有。
